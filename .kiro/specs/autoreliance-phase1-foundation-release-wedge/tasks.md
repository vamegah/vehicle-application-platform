# Implementation Plan: AutoReliance AI Phase 1 (Foundation and Release Wedge)

## Overview

This plan implements Phase 1 only: the shared foundation (monorepo, local environment, dependency ledger, contracts, shared libraries, API gateway, audit sink, observability) and the five problem modules. The modules are five bounded contexts (`data-readiness`, `legacy-integration`, `integration-intelligence`, `configuration-assurance`, `release-assurance`) packaged, together with `api-gateway` and `audit-sink`, into five deployables: `data-platform`, `integration-config`, `release-assurance`, `api-gateway`, and `audit-sink` (design: "Deployable Topology", ADR-005). Directories stay one per bounded context under `services/`; the deployables are packaging units under `platform/`.

Languages follow the design and `tech.md`: Python 3.12/FastAPI for `data-readiness` and the inference sidecar; Java 21/Spring Boot 4.1.x with Spring Cloud 2025.1.x and Jackson 3 (Maven; ADR-006) for `legacy-integration`, `integration-intelligence`, `configuration-assurance`, `release-assurance`, `api-gateway`, and `audit-sink`; Next.js/React/TypeScript/Tailwind CSS for `apps/web`. Property tests use Hypothesis (Python) and jqwik (Java).

Ordering rules:

- Contract-first: AsyncAPI 3.0 (tasks 2.1, 2.2, 2.8, and 2.9), protobuf (task 2.3), and OpenAPI 3.1 (task 2.4) are defined and validated before task 1.1 writes anything under `services/`, and so before any producer, consumer, or endpoint code. The `verify-contract` hook blocks a write under `services/<context>/` until that context has a contract. Every later implementation task that produces, consumes, or exposes a contract element depends on tasks 2.1 to 2.9.
- Execution order: task numbers are unchanged, and the Task Dependency Graph sets the order. The contract tasks 2.1, 2.2, 2.3, 2.4, 2.6 (buf CI), 2.8, and 2.9 run before task 1.1. Tasks 2.5 and 2.7 also define CI for contracts, but they check output of later tasks (2.5 runs the Kustomize build of task 1.6 and the Testcontainers suites; 2.7 commits generated clients into the modules of task 1.1), so they run after those tasks.
- Dependency-first: task 1.4 resolves and records exact versions before any manifest is written with a dependency (the contract tooling and task 1.1 onward).
- Each implementation sub-task lists its own acceptance criteria and its own tests. A sub-task is complete only when every listed test passes.
- Each correctness property from the design is its own sub-task, placed directly after the implementation it checks.
- Phase 2 to 4 modules are not implemented. They appear only as reserved event names (task 2.1) and a continuity check (task 21.1, `docs/phasing.md`).

Repository conventions used by every task (from `structure.md`, `api-standards.md`, `security.md`):

- Java code in `services/<context>/src/main/java/com/autoreliance/<context>/` (no hyphens in package names: `legacyintegration`, `integrationintelligence`, `configurationassurance`, `releaseassurance`, `apigateway`, `auditsink`). Python code in `services/<context>/app/<context>/` (underscores: `data_readiness`, `release_assurance`) with `main.py` as the FastAPI entrypoint.
- Contract files are named per context: `contracts/openapi/<context>.yaml`, `contracts/asyncapi/<context>.yaml`, `contracts/proto/<context>/`, plus the aggregate `contracts/openapi/gateway.yaml`. The three risk topics, `document.text.extracted`, and the four ERP and MES topics (`erp.masterdata.changed`, `erp.purchaseorder.updated`, `mes.workorder.reported`, `mes.quality.inspection.recorded`) have one AsyncAPI file each, named for the topic. The per-context files `legacy-integration.yaml` and `data-readiness.yaml` reference those topic files and do not redefine them. There is no `document.extraction.requested` topic and no combined `source.record.extracted` topic.
- Cross-cutting decisions: Spring Boot 4.1.x with Jackson 3 (ADR-006), Kustomize `base/` and overlays with no Helm (ADR-007), PDF text only through the `document.text.extracted` event and ERP and MES records only through four domain topics, with data paths Kafka-only and the `/admin/*` cache read as the sole synchronous HTTP between `data-readiness` and `legacy-integration` (ADR-008, ADR-011, ADR-024), single-replica scheduling with no ShedLock, redbeat, or Quartz (ADR-009), `spring-vault-core` pinned to 4.1.2 (ADR-010), and PDF bytes in an S3-compatible object store behind a `StorageProvider` port with only metadata and the object URI in PostgreSQL (ADR-012), Garage as the digest-pinned local backend (ADR-013, ADR-019), SeaweedFS as a digest-pinned CI smoke-test container that is never release evidence (ADR-020) and as the approved dev-backend alternative under the ADR-019 switch trigger, not running in dev, a single approver for the dedicated-bucket exception in Phase 1 and a layout value read once and cached (ADR-021, with the onboarding runbook, three-phase layout change, and Phase 2 refresh trigger of ADR-022), two shared buckets per environment (`autoreliance-raw-{env}`, `autoreliance-text-{env}`) with tenant key prefixes, prefix-scoped IAM on AWS S3 and Ceph RGW, a documented dev-only gap where Garage cannot enforce tenant prefixes at the store, and dedicated per-tenant buckets only through an approved exception path (ADR-014 as amended by ADR-018), a production encryption guard that requires the per-tenant key strategy (ADR-015), and the source key strategy for the ERP and MES topics (ADR-016, ADR-017).
- Data paths are Kafka-only. No service-initiated synchronous HTTP exists between bounded contexts for data-plane operations (extraction, ingest, query, mutation). Admin paths under /admin/* are the sole exception: they may use synchronous HTTP between services for read-only diagnostics, gated by platform-operator role and audited. Any admin-path HTTP failure returns 503 to the caller; no fallback, no cached value. (ADR-024; gateway-to-service routing is not service-initiated and the gRPC contracts are not "synchronous HTTP" under this rule.) Internal cache routes are served on the `admin-cache` management port (8081/TCP) behind a NetworkPolicy.
- REST under `/api/v1/<context>/`, success envelope `{ "data", "meta": { "traceId", "tenantId" } }`, errors as `application/problem+json`, cursor-only pagination.
- Event envelope `{ eventId, eventType, version, tenantId, occurredAt, payload }` with W3C trace context in Kafka record headers. The five `legacy-integration` topics use the source-ingestion envelope: the base envelope plus `sourceSystem`, `naturalKey`, `contentHash`, `extractedAt`, and an optional `sourceRecordVersion` (ADR-016, ADR-017; recorded in `api-standards.md`). Topic names follow `<domain>.<entity>.<action>` with exactly two exceptions: `dlt.<consumer-group-id>` and `mes.quality.inspection.recorded`.
- Each bounded context has its own PostgreSQL schema and login role, even inside a shared deployable. Java contexts migrate with Flyway; Python components migrate with Alembic.

- **Definition of Done for every task (`validation.md`).** A task is complete only when its own tests pass and all of these hold for what it changed:
  - Every new API endpoint has an OpenAPI 3.1 entry in `contracts/openapi/`.
  - Every new Kafka producer or consumer has an AsyncAPI entry in `contracts/asyncapi/`.
  - Every dependency added has an exact pin in the manifest and a row in `DEPENDENCIES.lock.md`.
  - Every tenant-scoped query has a test proving tenant A cannot read tenant B data.
  - Every AI-generated conclusion has a test asserting at least one evidence citation.
  - Redis broker and cache are separate instances in production config; the Spring Cloud BOM version is pinned in the ledger; Flyway and Alembic are both configured (one per runtime); generated OpenAPI clients are drift-checked in CI; the buf breaking check runs on every `contracts/proto/` change; `release-assurance` does not consume `release.risk.scored`; the Phase 1 ML scope of the sidecar is documented.
- **Manual review gates (`validation.md`, do not auto-approve).** `design.md` proposes no shared database and no separate vector database; this file contains no Phase 2 to 4 service tasks (only the documentation task 21.1).
- Deviation from the workflow default: test sub-tasks are not marked optional (`*`), because the request requires every task to carry its own tests and to stay incomplete until they pass. Property test sub-tasks are required for the same reason.
- Contract-first gate: the contract tasks 2.1, 2.2, 2.3, 2.4, 2.6, 2.8, and 2.9 precede task 1.1 and all producer, consumer, and endpoint code, and the dependency graph places them before every later wave that touches those contracts. Tasks 2.5 and 2.7 run after tasks 1.6 and 1.1, whose output they check. The repository's contract hook looks for `contracts/openapi/<service>.yaml`, `contracts/asyncapi/<service>.yaml`, or `contracts/proto/<service>/` for each changed `services/<service>/`, so every context keeps those per-context files even though the three risk topics also have per-topic files.
- Dependency-first gate: task 1.4 precedes every manifest. Versions are resolved and verified at execution time. Libraries beyond the brief are limited to the five approved in ADR-003 and the object-storage additions approved in ADR-012 (AWS SDK for Java v2 `s3`, boto3, and the digest-pinned Garage image, ADR-013); anything else needs user approval. `spring-vault-core` is pinned to 4.1.2 (ADR-010).
- Directories are one per bounded context under `services/` as required by `structure.md`. The five deployables are packaging units under `platform/` (task 1.6). The repository hooks (`verify-contract.ps1`, `check-phase-scope.ps1`, `run-affected-tests.ps1`) list service names and need user edits for `legacy-integration`, `configuration-assurance`, `api-gateway`, and `audit-sink`, and `run-affected-tests.ps1` needs a branch for the sidecar. - Spring Boot 4.1.x with Spring Cloud 2025.1.x is the pinned line (ADR-006). Boot 4.1 has a bounded OSS window, so planning the next Boot upgrade is a follow-up outside Phase 1.

The default layout is two shared buckets per environment (`autoreliance-raw-{env}` and `autoreliance-text-{env}`) with tenant key prefixes (ADR-018). A dedicated bucket pair is an opt-in exception through the documented approval path (task 7.12).
